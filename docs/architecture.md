# 技术原理与实现边界

## 1. 整体架构

本项目采用指令型 Agent Skill：通过结构化文本影响助手的任务判断，再由助手调用环境中的文件、终端、浏览器或媒体工具完成工作。它没有自建 API 服务、数据库、任务队列或模型推理代码。

| 层次 | 实现载体 | 负责什么 |
| --- | --- | --- |
| 技能发现 | `SKILL.md` 的 YAML frontmatter | `name` 标识技能，`description` 描述适用任务 |
| 任务编排 | `SKILL.md` 的 Markdown 正文 | 判断范围、读取设计约定、选择所需能力、形成交付 |
| 专项知识 | 三份 `references/*.md` | 只在内容、媒体或本地交付任务出现时加载 |
| 客户端展示 | `agents/openai.yaml` | 展示名称、简短说明、默认提示词；保持自动发现 |
| 外部执行 | 宿主的模型、工具和已安装技能 | 修改文件、构建网页、检查页面、处理素材 |
| 仓库验证 | Python 标准库脚本 | 检查文件、基础元数据、内部链接和可移植性 |

发现、主体加载、参考资料按需读取符合 Agent Skills 的渐进式信息披露方式。具体客户端的加载机制以其实现为准。[OpenAI 技能说明](https://developers.openai.com/plugins/concepts/skills)

## 2. 从输入到交付

输入通常包括需求、目标文件或路由、现有页面、项目说明、设计约定和原始素材。助手先确定“修改什么”，再决定“需要读哪些内容、用哪些工具”。

```text
目标与范围
  → 当前实现 + PRODUCT.md / DESIGN.md（存在时）
  → 局部修改 / 整站设计 / 内容审查 / 媒体集成 / 本地交付
  → 当前任务需要的参考指南和已安装能力
  → 本地源文件改动
  → 关联内容同步
  → 真实页面、媒体或归档验证
  → 文件、结果与发布状态
```

这些模式可组合。例如“修改按钮并更新上传包”同时涉及内容一致性和交付，但不需要重新生成主视觉。

## 3. 设计约定如何协调多个技能

`PRODUCT.md` 可以解释受众、使用场景、产品事实和核心任务；`DESIGN.md` 可以记录字体、色彩变量、间距、组件、素材和交互约定。两者都以项目现有内容为准，不要求每次任务都创建新文档。

三个核心设计角色各司其职：视觉方向确定页面如何表达主题；实现与精修关注使用体验；设计复核检查是否泛化、重复或脱离简报。它们共享同一份设计约定，不各自输出互相矛盾的设计系统。

冲突时遵守宿主的指令层级与权限规则；在设计选择上以用户当前明确要求为准，再结合项目事实处理。技能提供的示例颜色、字体、主题不应覆盖项目品牌。仅局部修改时保留已有设计。

## 4. 关联一致性为何不是全局替换

同一概念可能在主标题、短导航名、`aria-label`、说明文字、FAQ、示例和下载内容中用不同措辞表达。只搜索一个字符串会漏掉依赖；无条件替换又会损坏无关内容或历史证据。

工作流要求按语义建立本次改动的影响范围，再逐处核对。稳定 URL 与锚点一般无需跟着展示文案改名；原始报告中的历史标题也不应为了页面文案一致而被改写。

示例：“顺序执行”改成“可选路径”时，除了标题，还要检查上一项/下一项的含义、前置条件和说明。用户若明确要求只改一处，则报告相关矛盾，不擅自扩大改动。

## 5. 可移植的能力发现

公开版通过当前宿主提供的技能目录找到入口，不依赖作者的绝对路径，也不假定所有技能位于相邻目录。插件前缀、版本目录和启动脚本可能不同，应读取当前实际入口。

配套技能缺失时，继续执行基础分流、设计约定、一致性和验收流程。缺少工具会影响实际能力：没有浏览器不能声称已看过页面，没有渲染器不能声称已导出视频。仅有一个技能文件也不代表获得对应服务权限。

`agents/openai.yaml` 没有声明 MCP 服务端依赖；其中不能把其他 skill 名称伪装成 MCP 连接。模型自行选择工具不等于本项目实现了工具协议或后台调度器。

## 6. 网页中的技术点

以下是工作流会检查或协调的技术，不是安装此 skill 时需要全部安装的依赖。

| 技术或机制 | 何时涉及 | 关注点 |
| --- | --- | --- |
| HTML、CSS、JavaScript 与已有框架 | 页面实现 | 保留项目技术栈、语义结构、响应式布局和交互状态 |
| Design tokens | 视觉统一 | 色彩、字体、间距等以项目已有变量为准 |
| 可访问性 | 受影响的布局与控件 | 键盘、焦点、名称、可读性、减少动效偏好 |
| 原生 HTML 视频播放器 | 普通教程视频 | 播放、暂停、拖动、浏览器支持的倍速与全屏 |
| HTTP Range、媒体元数据 | 视频无法拖动等问题 | 检查真实资源与服务行为，避免直接堆自定义控件 |
| 原始二维码图像与解码工具 | 页面或海报二维码 | 模块、留白、对比度、显示尺寸与实际识别结果 |
| WebGPU / Shaders | 有明确价值的实时视觉效果 | 设备支持、性能、静态后备、文字和操作可用性 |
| Remotion / HyperFrames 等 | 已请求的视频制作 | 沿用工程、稳定运镜、关键证据、导出后回看 |
| 相对路径、base path、路由 | 子目录部署 | 直接进入、刷新、动态资源、字体与下载链接 |
| ZIP、文件清单与哈希 | 交付包 | 资源完整、版本一致、增量与完整站点标识 |

Shaders 使用 WebGPU，并可用于多种前端框架；是否引入应由项目需求决定。[Shaders 官方说明](https://shaders.com/docs/guide)

## 7. 状态、隐私与执行范围

本仓库不包含联网执行程序、遥测、密钥、个人网站文件或账户配置。校验脚本仅读取仓库文件。助手执行任务时是否向模型或工具发送内容，取决于宿主与实际调用的服务；不能由“文件在本地”推断全部处理离线。

项目的持久状态是源文件、设计约定和已有交付目录。临时输入、示例用途、生成结果是否过期等状态属于目标网页，应按现有产品交互处理，不能用 skill 的描述代替实际实现。

用户要求本地交付时，不自动建立托管副本。准备 GitHub 文件、打包网站和发布网站分别对应不同动作；只有任务范围包含发布，才使用既定发布方式。

## 8. 验证能力的边界

仓库脚本检查结构，格式校验检查技能元数据；二者都不能证明网页美观、视频流畅或用户价值表达正确。后者需要在具体项目中检验，详见 [验证方法](validation.md)。

本项目没有训练专用模型，没有输出质量跑分，也未验证全部客户端或全部可选工具组合。它提供可读、可审查、可版本管理的方法，帮助使用者稳定完成从修改到交付的过程。
