# Content clarity and related consistency

Read this for solution pages, whole-page value reviews, or wording changes with related uses. Use the relevant sections for a small edit; do not turn a local request into an unsolicited content overhaul.

## Review the visitor's path

Use the known audience, use scene, product behavior, and existing evidence. Identify which question each section should answer:

- What problem does this solve, and for whom?
- When should the visitor choose this capability or path?
- What input and preparation are required?
- What happens, what is produced, and what can that result help them decide?
- What specific action can they take next, and where does it happen?

Read the hero, the route explanation, each module, examples, and handoff materials as one path. A headline names the point; supporting copy adds information rather than repeating it. Replace vague benefits with supported actions and outcomes, not invented metrics, customer results, or guarantees. Expand unfamiliar terms where the explanation helps a decision, rather than adding a glossary by default.

For an authorized whole-page improvement, fix the meaningful clarity problems directly. For a critique-only request, report concrete findings. Keep the established audience and aesthetic; copy review is not permission to replace the site's identity.

## Model the actual relationship

Determine whether modules are alternatives, complementary paths, prerequisites, or sequential actions. Numbering and pager labels should not imply that every tool must run in order when the visitor can choose among them. Preserve an established browsing order when useful, but explain optionality and dependencies in plain language.

Distinguish inputs, collected data, analysis, recommendations, and validated effects. Explain the handoff between them: which tool produces the raw material, who interprets it, and how a conclusion can be checked. Do not imply that saving a file also generated a report, or that producing a recommendation already improved a business outcome.

Separate the example's default behavior from capabilities requiring setup. For example, “This example saves a local file; a shared destination requires an output configuration” is clearer than implying both destinations work automatically. Keep prerequisites near the relevant action instead of repeating a full setup checklist everywhere.

Use the project's actual evidence for feature and access claims. Reverify changeable prices, quotas, eligibility, or platform limitations when retaining a precise claim; otherwise use an appropriately qualified reference to current product conditions. Do not fill missing facts with a plausible implementation.

## Synchronize a local change by meaning

1. Identify the concept and the user's boundary from the selected region or wording request.
2. Inspect affected navigation, section titles, accessible names, explanatory text, FAQs, empty states, examples, downloadable materials, and the active build/package. Check semantic dependencies as well as exact text matches.
3. Update representations that would otherwise contradict the change. Keep unrelated occurrences, stable anchors, and external contracts intact unless their change is required.
4. If the requested text changes the underlying relationship, reconcile that relationship in the adjacent explanation and controls. If the user explicitly requested only one location, flag the conflict rather than broadening the edit.

A request to remove an unused media promise also affects “coming soon” FAQs and download instructions. It does not automatically authorize deleting original recordings from disk. A rename that fixes a visible heading may also require the navigation label and accessible name; shorter wording can differ if it still describes the same destination accurately.

## Make actions and examples usable

- Name the actual action and destination: view a tutorial, download a source document, obtain an application, copy a parameter, or generate an example. A generic “Learn more” needs a clear surrounding context.
- Clarify whether an interaction updates example text, downloads material, or actually executes a task. Do not present a local form submission as a completed external operation.
- State where copied text belongs and what must already be connected or configured. When several capabilities share an example area, make the current purpose visible and provide a simple way to choose it when otherwise ambiguous.
- Check each input's role in the output. Include relevant context in generated text; if a field does not apply to a particular purpose, explain that or scope the field rather than silently ignoring it.
- Follow edits through update, purpose switching, copy, and download. Prevent accidental use of an outdated result using the existing interaction model: update automatically when appropriate, or clearly mark pending changes and require the existing update action. Do not add controls where a label fix is enough.
- Success and failure copy should describe the actual state. Distinguish a generated draft from a tested workflow, saved preferences from unsaved edits, and a completed execution from a failed or empty result. Delayed feedback must not restore a label belonging to a previous selection.

## Protect evidence while clarifying it

Identify historical samples, synthetic illustrations, edited recordings, and test inputs honestly. Preserve the original report, prompt, screenshot, and recording unless the user asks to change the source itself. Explanatory summaries can be rewritten; evidence and its time/sample context must remain attributable.

For monitoring or comparison examples, retain channel, time, question, and sample distinctions that affect interpretation. A failed collection is not a negative finding. An explicitly named-brand question and a neutral recommendation question answer different research questions; do not combine them into an unsupported visibility claim.

## Verify the changed path

Check the affected text in its visible context, accessible name, and downloadable counterpart. For forms, try a realistic changed profile and purpose switch, verify copy/download against the displayed result, and restore temporary test inputs. Inspect longer labels at relevant widths. Scale validation to the edit: a local rename needs a dependency check, while an interactive example change needs an interaction check.
